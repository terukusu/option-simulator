# ADR-0014: シナリオの点・テール・追証の線の証拠金を JSCC のシナリオの当て直しにする

- 状態: 採択（2026-11-23）
- 日付: 2026-11-23
- 関連: #387、#383（Spike）、#382・[ADR-0013](adr-0013-margin-now-jscc-var.md)（今の JSCC の計算）、[ADR-0002](adr-0002-margin-grid-approximation.md)（格子の概算）、optionchan の #168（r・g の派生の表）、`docs/design.md` 5.10・4.1・7.1・7.3・13.1 K14・13.3 R10

## 背景

- #382 で「今」の必要証拠金は JSCC の VaR 証拠金の計算になり、口座の額と ±200 円で合った。シナリオの点（ΔX・Δσ・d を動かした先）・テールの証拠金の表・追証の線は格子の概算のままで、今のすぐ隣の点で値が跳ぶ（#383 の観測: 格子 ÷ JSCC は「相殺する」で中央値 0.89・p90 1.33、形により 0.65〜1.4 倍）
- #383 で、JSCC のシナリオ（BPF の銘柄ごとのシナリオの値）は、限月ごとの先物の対数リターン r と、標準化 moneyness z をキーにした IV の対数変化 g(z)（13 節点の折れ線）と、2 営業日先までの暦日の時間経過 h で表せると分かった。当てはめた r・g を動かした先の状態に当て直すと、ES の誤差は同じ日で中央値 0.2%・p90 1.6%、別の日の動きで中央値 1.3%・p90 3.2%（カレンダーは最大 16%）。値は書かない（JSCC のサイト利用案内）

## 決定

1. シナリオの点・テール・追証の線（損益グラフ・保有ポジションの一覧の合計）と AI のツール（margin_summary の point・call_levels、tail_table）の証拠金を、基準日（今の JSCC と同じ）の r・g を状態 S に当て直した VaR 証拠金額にする（`model/jsccRefit.ts`）: F′ = F_S e^{r_j}、σ′ = max(σ_min, σ_S exp(g_j(z_S)))、T′ = T_S − h_S、OP の 1 単位 = max(1, round(Black-76))、先物 = 1 枚のシナリオの損益。v_j の和の ES は #382 と同じ関数、V_S = max(0, ES, ceil(−NOV_S))、必要証拠金 = k·V_S、所要額 = max(0, k·V_S − NOV_S)
2. **r・g は optionchan が毎日当てはめた派生の表**（`jscc_var_scenario_factor`。optionchan の #168）を simulator の API（`GET /api/jscc_factors`）が整数に量子化して返すだけ。当てはめは optionchan の取り込みのジョブで 1 日 1 回
3. 今（シナリオ 0）は #382 の正確な値のまま。今と当て直しの差は補正せず、内訳に「今を推定で」の 1 行を出して跳びの大きさを見せる
4. r・g が無い・当て直せない（限月の行が無い・枚数が整数でない）ときは格子の概算に戻し、理由を出す。出どころは文字で 3 種（`JSCC 11/20` / `JSCC 推定 11/20` / `概算`）
5. テールと追証の線は操作が止まってから（120 ms）、1 切れ = 状態 1 つの生成器を 8 ms ずつ回して作る。追証の線の二分法は区間の両端の裾の候補（H の小さい方から 4 × 裾の本数 + S の全部）だけで評価し、収束した区間の両端を全シナリオで確かめる（外れたら全シナリオでやり直す = 根は全シナリオの二分法の根のどれか（1 円以内）。区間に根が 2 つ以上あると別の根を返しうる）
6. 推定の質（optionchan が毎日記録する、基準の状態で当て直した 1 枚の売りの ES と JSCC の値の相対誤差の中央値・90 パーセンタイル）を限月ごとに返して内訳に出す。中央値が 5% を超える限月がある日は使わず、直近の質のよい日の JSCC で推定する（決定 7。どの日もだめなら格子）。90 パーセンタイルが 5% を超える限月は印に「誤差大」を付けて当て直す（期近は翼の 1 円の下限に張り付く銘柄で p90 が大きくなりやすいが中央値は小さい。期近は利用者の主な限月なので p90 だけで使わないと目的を外す）
7. **戻る先の順**（オーナーの承認 2026-11-23「正確になるように」）: 基準日の BPF（今）→ 基準日か、それより前で直近の使える日の r・g で今の状態を当て直した値（JSCC 推定。印に使った日）→ 格子（どの日も使えないときだけ）。遡りは API が JSCC の営業日で 10 日まで（数日ではシナリオの規模はほぼ変わらない（#383 で確かめた 2 日の比は 1% 程度）が、急変の後は EWMA で規模が変わるので遠い日は使わない）。限月の質が閾値を超える日は、すべての限月の質がよい直近の日に戻る（シナリオの並びは日ごとに違い、1 つのポートフォリオは 1 日のシナリオで組む）。平日 17:00〜18:30 は前の営業日の JSCC で推定する（#382 の not_ready → 概算を置き換え）。前の日の BPF の値をそのまま今に使わないのは、日がずれると建玉・価格が違うため
8. h は格子と同じ「S から 2 営業日後までの暦日」（#383 で BPF と合った。D14 は変えない）。h の間に SQ がある足は本源的価値（格子と同じ）。動かした先での EWMA のスケールし直しは入れない（下げの点で数 % 小さめ。開示する）

## 選ばなかった案

- **simulator の API で r・g を当てはめる**: 依存を足さず純 Python で書けるが、手元の計測（合成）で 1 限月 2.5〜10 秒の CPU。Cloud Run は 1 vCPU・gunicorn 1 ワーカーなので、その間ほかの要求（板）が GIL で止まる。インスタンスが冷えるたびに繰り返す。numpy なら速いが依存の追加。optionchan の依頼が通らないときの代替として残す
- **ブラウザで当てはめる**: 「計算はブラウザ」には最も忠実だが、行使価格 40 本 × 1,422 本の値を毎日読む（限月あたり約 5 倍の応答）うえ、IV の逆算を毎回する
- **今の値（BPF）への足し算・掛け算の補正**: 今と隣の点の差には前営業日の引けから今までの相場の動き（本物の差）が混ざるので、それまで消してしまう。当て直しの誤差だけを分けるには基準の状態（清算値段の IV）をブラウザで組む必要があり、手間に見合わない
- **Web Worker**: 足の IV の基準（`sigmaBase`）が関数で postMessage で渡せず、ワーカーの中で板から足を作り直す大きな作り替えになる。切れごとに回せば描画のフレームは守れる
- **追証の線だけ格子**: テールの証拠金の表（当て直し）と追証の線（格子）で余力の符号の変わる所がずれる
- **EWMA の係数を足す**: #383 の 1 つの見積もり（−5% の 2 日で約 4%）から係数を作ると検証できない。#165 の過去分で連続した日の r の比から確かめてから

## 結果

- シナリオの点・テール・追証の線が今の値と同じ物差し（JSCC のシナリオ）になる。今のすぐ隣の点の跳びは、前営業日からの相場の動きと当て直しの誤差（同じ日で中央値 0.2%・p90 1.6%）の分だけになる
- テールの証拠金の表は操作中に前の値を「計算中…」で残し、止まってから更新される
- 足が多い（保有の合計 160 本など）と 1 切れが 16 ms を超えうる（記録だけ）
- 精度は 2 日分の BPF での確認だけ。別の日の動きで p90 3.2%、カレンダーは最大 16%、下げの点は EWMA の分だけ数 % 小さめ、年末・連休の h と SQ をまたぐ足は未確認。optionchan の表の照合の列で日々の当てはめの質を見られる
- 追証マップ・過去の急落の再生・売りの効率・形のカード・AI の提案は格子のまま
- 1 日のクエリ量の増分は (日) ごとに 1 回 × インスタンス、最小課金 10 MiB

## 詳細（設計 5.10 から。AI が節ごとに読む設計書の大きさに収めるためこちらに置く）

当て直し（`model/jsccRefit.ts`）: 基準日（今と同じ）の JSCC のシナリオを、限月ごとの先物の対数リターン r_j と、標準化 moneyness z をキーにした IV の対数変化 g_j(z)（13 節点 {−5, −4, −3, −2, −1.5, −1, −0.5, 0, 0.5, 1, 1.5, 2, 3} の折れ線。節点の外は端の値）に分けたもの（#383 の手順で optionchan が毎日当てはめた派生の表。4.1・R10）を状態 S に当て直す。

- 足ごと（M の足は今と同じ。枚数が整数でなければ当て直せない）: F_S = 状態 S の足の原資産、σ_S = `legSigma`（β・Δσ・Δs・動き方・スマイル込み）、T_S = T₀ − d、h_S = S から 2 営業日後までの暦日（格子と同じ `businessDaysAhead`。#383 で BPF の σ√T の変化が暦日に合った。D14 は変えない）、z_S = ln(K / F_S) / (σ_ATM,S √T_S)（σ_ATM,S = 限月のスマイルの ATM をシナリオで動かした σ。スマイルが無ければ足の σ の基準）
- シナリオ j: F′ = F_S e^{r_j}、σ′ = max(σ_min, σ_S exp(g_j(z_S)))、T′ = T_S − h_S。OP の 1 単位の値 = max(1, round(Black-76(F′, K, T′, σ′)))（T′ ≤ tMin は割引本源的価値、T′ ≤ 0 は本源的価値 = h の間に SQ がある足は格子と同じ扱い。どれも下限 1 円）。1 枚の値は OP = 乗数 × 値、先物 = round(乗数 × F_S (e^{r_j} − 1))（シナリオの損益）の整数で、符号 × 枚数を掛けて足す（BPF の pnl と同じ足し方）
- v_j の和 → 今と同じ ES（`jsccEsSigned`）→ **V_S = max(0, ES, ceil(−NOV_S))**、必要証拠金 = k × V_S、所要額 = max(0, k × V_S − NOV_S)。NOV_S・先物の評価損益・清算額・値洗いは格子と同じ（`marginLegs`）
- 行の引き方: OP の足は `NK225E-YYYYMM` の行（g が空 = 当てはめられなかった限月は IV を動かさない）、先物の足は限月で引き商品は問わない（自分の商品 → 同じ限月の NK225E → ほかの先物）。OP の足に限月の OP の行が無ければ当て直せない
- **遡り**（#387。API `/api/jscc_factors` がする）: 基準日から JSCC の営業日（取り込みの succeeded のある日）を新しい順に 10 日まで見て、要求の限月がすべて表にあり、OP の行の推定の質（中央値）が閾値以下の最も新しい日を使う（限月ごとに日を変えない = シナリオの並びは日ごとに違い、1 つのポートフォリオの ES は 1 日のシナリオでしか組めないため。質の悪い限月がある日は、すべての限月の質がよい直近の日に戻る）。使える日が無ければ `no_recent`（格子 + 理由「直近 10 営業日に使える JSCC のデータが無い」）。10 営業日の根拠: 数日ではシナリオの規模はほぼ変わらない（#383 で確かめた 2 日の比は 1% 程度）だが、急変の後は EWMA でシナリオの規模が変わるので遠い日は使わない。遡った応答は Cache-Control を短く（60 秒）し、画面も 5 分後の板の読み直しで基準日の表に替える（基準日の表の ok だけを読み直さない）
- **推定の質**（optionchan の表の `check_median_rel`・`check_p90_rel` = 基準の状態で当て直した 1 枚の売りの ES と JSCC の値の相対誤差の中央値・90 パーセンタイル。API がそのまま返す）: 当て直す OP の足の限月の中央値が **5%（`JSCC_REFIT_MAX_MEDIAN_REL`）を超える限月がある日は使わず、直近の質のよい日に遡る**（API。画面の `poor_fit` = 格子は、それでも閾値を超える行が来たときの守り）、90 パーセンタイルが **5%（`JSCC_REFIT_WIDE_P90_REL`）を超える限月があれば印に「誤差大」**（`JSCC 推定 11/20・誤差大`）を付けて当て直す。内訳に「推定の誤差」の行（限月ごとに中央値・p90）。理由: 期近は利用者の主な限月で、質の悪さだけで格子に戻すと目的を外す（実データ（2026-11 の 5 日）で、期近の限月は翼の 1 円の下限に張り付く銘柄の相対誤差で p90 が 5% を大きく超えるが中央値は小さく、ほかの限月は中央値・p90 とも 1〜2% 程度以下）。中央値が 5% を超えるのは当てはめが壊れた限月と読む（#383 の同じ日の当て直しの誤差は 104 ポジションで p90 1.5%・最大 7%）。実データで直してよい
- 当て直せないときは格子の概算 + 理由（読み込み中・基準日のデータがまだ無い・限月の行が無い・推定の誤差が大きい・枚数が整数でない・読めない・データ元に無い。今の JSCC と同じ理由の文）。基準の状態（今）で当て直すと BPF の値に近い（#383: 同じ日の当て直しの ES の誤差は 86 ポジションで中央値 0.2%・p90 1.6%）
- **今の点との跳び**: 今は BPF の値そのもの（前営業日の清算値の状態）、今以外の点は今の板から動かした状態の当て直し（下の「S を引けの後と読む」と同じ）。差には前営業日の引けから今までの相場の動きと当て直しの誤差が混ざるので補正しない。内訳に「今を推定で」（今の状態の当て直しの必要証拠金。今が JSCC で r・g があるときだけ）を出して跳びの大きさを見せる
- **EWMA**: 基準日の r を毎日取り直すので今の水準は入る。動かした先（下げ）での EWMA のスケールし直しは入れない（#383 の見積もりで −5% の 2 日で先物のシナリオが約 4% 大きくなる分、下げの点で数 % 小さめ）。根拠の無い係数は足さず、ⓘ・マニュアルに開示。#165 の過去分で確かめる後続
- 精度（#383。2 日分の BPF。値は書かない）: 別の日の動きを当てると中央値 1.3%・p90 3.2%、カレンダー（限月違い）は最大 16%、限月違いの先物 7%。期近の翼（z < −5、1 円の下限）は相対誤差が大きい。年末年始・連休の h と、h の間に SQ がある限月は未確認（#165 の過去分の年末の BPF で確かめる後続）
- 読み込み（`ui/components/useJsccFactors.ts`・`/api/jscc_factors`。7.1）: 基準日と限月の集合（足の OP・先物の限月）が変わったとき・メモリから追い出されたときに読む。規則は今の JSCC と同じ（自動のポーリングなし、not_ready・失敗は 5 分聞き直さない、板の読み直しで期限切れを読み直す、LRU 8 件）。dev の合成の板は `/fixtures/jscc_factors`（合成の板 latest の基準日だけ ok。#382 の合成のシナリオと同じ動き = r = ln(1 + 変化率)・g = ln(IV の倍率) を節点で同じ値）
- **計算の時機と性能**: シナリオの点は描画のたびに 1 状態（足 n × 1,422 の Black-76 + 並べ替え 1 回。足 10 本で数 ms。`tests/ui/perf.test.ts` の #131 AC17 のスライダー 1 回）。テールと追証の線は **操作が止まってから**（`MARGIN_LINE_SETTLE_MS` 120 ms）、1 切れ = 状態 1 つの生成器（`marginTailSteps`・`marginLineSteps`）を 8 ms ずつ `setTimeout(0)` で回す（`ui/components/useSettledSteps.ts`。追証マップの列ごとと同じ考え方）。テールは作っている間、前の行を残して注記に「計算中…」。格子のときも同じ経路。追証の線の二分法は、区間の両端の値（全シナリオ）から裾の候補（H の小さい方から 4 × 裾の本数 + S の全部）を決めてその候補だけで評価し、収束した区間の両端を全シナリオで確かめる（符号が違えば採用、同じなら全シナリオで二分法をやり直す = 根は全シナリオの二分法と 1 円以内で同じ。`tests/model/jsccRefit.test.ts` の種つき乱数のポジション 200 件）。保有ポジションの合計（足が多い）は 1 切れが 16 ms を超えうる（記録だけ）
- 画面の印: シナリオの点・テールの出どころは `JSCC 推定 11/20`（基準日の M/D）。全文の 1 行目 `必要証拠金（JSCC 推定 11/20）`、内訳の「点の計算」の行、テールの証拠金の表の注記 `JSCC 推定 11/20 · 2 営業日 · 掛け目 100%`（値動き幅・IV の幅は使わない。格子のときは今までの前提と理由）。内訳の群の見出しは今が JSCC で点・テールが当て直しなら「証拠金（今は JSCC の計算・他は JSCC 推定）」。AI のツールは `margin_summary.point.source`（`jscc` / `jscc_refit` / `estimate`）と `jscc_business_date`、`tail_table` の行に `margin_source`
