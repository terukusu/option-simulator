# option-simulator 設計メモ（たたき台）

日経225オプションの **建てる前の戦略検討** に使う損益シミュレーター。optionchan（JPX のページから毎分取り込んだ価格・IV を BigQuery に蓄積するツール）のデータを初期値に使う。

状態: たたき台（2026-10-13）。「6. 置き場所」は未決定で、この文書のレビューで決める。

## 1. なぜ作るか

既存のシミュレーター（証券会社のツールなど）の不満:

| 不満 | この PJ での扱い |
|---|---|
| IV を全行使価格で 1 つにする（スマイルを無視）。OTM の売りのリスクが小さく見える | 行使価格ごとの IV（板の IV / bid・ask の IV）で評価する |
| 行使価格・価格を毎回手で入れる | 最新の板を読み込み、スマイルカーブや板からクリックで足を追加する |
| シナリオが「満期」と「今」だけ。日数・原資産・IV を同時に動かせない | 日数・原資産・IV（水準とスキュー）をスライダーで同時に動かす |
| 戦略を並べて比べられない | 後段（7 章）で複数戦略の比較 |
| 操作のたびに再読み込みで重い | 計算はブラウザで行い、描き直しに通信しない |

## 2. スコープ

**最初に作るもの（MVP）**

1. 最新の板（2 限月分）の読み込みと表示: 原資産（日経平均・同限月の先物）、行使価格ごとの call / put の価格・bid / ask・IV、ATM、スマイルカーブ
2. ポジションの組み立て: 板・スマイルカーブから足を追加（売買・枚数・建値は板の値を初期値に編集可）。先物（ラージ / ミニ）も足にできる
3. 損益グラフ: 横軸は原資産価格。満期の損益と、指定日の理論損益を重ねる
4. シナリオのスライダー: 経過日数、原資産、IV の平行移動、IV のスキューの傾き
5. 指標: 損益分岐点、最大利益 / 最大損失（無限なら明示）、ポジション合計のデルタ・ガンマ・セータ・ベガ
6. 戦略テンプレート: ストラングル / ストラドル（売り・買い）、バーティカル、アイアンコンドル、バタフライ、カレンダー、レシオ。ATM・デルタ・距離で行使価格を選んで一括で組む

**スコープ外（MVP では作らない）**: 発注・口座連携、保有ポジションの管理・損益の記録、バックテスト、証拠金の正確な計算（7 章で目安のみ検討）

## 3. 前提（商品）

| 項目 | 値 |
|---|---|
| 対象 | 日経225オプション（ラージ、乗数 1,000）。日経225ミニオプション（乗数 100）は後で追加できるようにする |
| 先物 | 日経225先物（ラージ 1,000 / ミニ 100 / マイクロ 10） |
| 行使 | ヨーロピアン。権利行使日は SQ 日（毎月第 2 金曜。休業日なら前営業日）、取引最終日はその前営業日 |
| 決済価格 | SQ 値（SQ 日の構成銘柄の始値で算出）。満期の損益は SQ 値で評価する |
| 限月 | optionchan が取り込むのは直近 2 限月（JPX のページの 1・2 限月）。それより先は MVP では扱わない |

## 4. 価格モデル

- **Black-76**（先物価格ベース）で評価する。原資産は同じ限月の先物価格 F（optionchan の `future_price`）。配当・金利の推定が要らず、日経平均の現物から配当落ちを見積もるより誤差が小さい
  - 先物の限月がオプションの限月と合わない（四半期限月以外）ときは、現物 S と最寄りの先物から F を補間する（要検討。代替は現物 + 配当なしの Black-Scholes）
- 金利 r は割引だけに使う（定数。初期値 0.5% 程度、設定で変更可）
- **満期までの時間**: SQ 日（SQ 値の確定は SQ 日の午前）までの暦日ベース `T = (SQ 日 09:00 JST − 評価時刻) / 365 日`。営業日ベース（休業日の時間価値を割り引く）は設定で切り替えられるようにする（要検討）
- **IV**:
  - 既定は板の IV（JPX 公表値）。bid / ask の IV があれば、建値側（買いは ask・売りは bid）の IV を使うオプションを付ける
  - 板に IV が無い行使価格（約定なし）は、近い行使価格の IV からスマイルを補間する（moneyness `ln(K/F)` に対する平滑化スプライン、または SVI の当てはめ。MVP は区分線形でよい）
  - シナリオの IV: `iv'(K) = iv(K) + 平行移動 + 傾き × ln(K/F)`。時間経過で IV を変えない（sticky strike）を既定にし、sticky moneyness を切り替えで選べるようにする（要検討）
- **グリーク**: Black-76 の解析解。表示単位はデルタ = 先物 1 枚相当、セータ = 1 日あたり円、ベガ = IV 1 ポイントあたり円
- **損益**: `Σ 枚数 × 乗数 × (評価価格 − 建値) × 売買の符号`。手数料は設定（1 枚あたり円）で引けるようにする

計算はすべてブラウザ（TypeScript）で行い、サーバーはデータを返すだけにする。描き直しは 1 フレーム（16ms）以内を目標にする（原資産の格子 200 点 × 足 10 本程度なら十分間に合う）。

## 5. データ

optionchan の BigQuery データセット（`optionchan_tokyo`）の最新スナップショットから読む（読み取り専用）。

| 用途 | テーブル / 列 |
|---|---|
| オプションの板 | `option_price`: `type`（1 = call / 2 = put）、`target_price`、`last_trading_day`、`price`・`bid`・`ask`、`iv`・`bid_iv`・`ask_iv`、`is_atm`、`volume`・`positions`、`delta`〜`vega`（JPX 公表値。照合用）、`price_time` |
| 先物 | `future_price`: `price`、`contract_month`、`price_time` |
| 現物 | `spot_price`: `price`、`price_time` |
| 鮮度 | `created_at`（スナップショット時刻）を画面に出す。時間外は直近の取引時間の最後の値 |

API（案）: `GET /api/chain` → 最新スナップショットの 2 限月分の板・先物・現物を 1 つの JSON で返す（1 回 数十 KB）。過去時点の板（`?at=`）は後段。

データ元はアダプタにして差し替えられるようにする:

- `bigquery`: optionchan の BigQuery から読む（本番）
- `file`: JSON / CSV を読み込む（GCP を持たない人、オフラインの検討、テスト）
- 手入力: 板が無くても、行使価格・価格・IV を手で入れて使える

## 6. 置き場所（未決定。ここをレビューで決める）

| 案 | 構成 | 長所 | 短所 |
|---|---|---|---|
| **A. 単独の Cloud Run + IAP** | このリポジトリに UI（静的ファイル）と小さな API を置き、optionchan と同じ GCP プロジェクトに Cloud Run サービスとしてデプロイ。IAP で自分だけに公開。API は読み取り専用の SA で `optionchan_tokyo` を読む | optionchan のビューアーと同じ作り（IAP・CI・Terraform・イメージのビルド）を流用できる。リポジトリが独立して育てやすい。どこからでもブラウザで使える | Terraform・CI・IAP の設定がもう 1 組要る（ビューアーで手順は確立済み）。OAuth クライアントを共用するか別に作るかを決める |
| **B. optionchan のビューアーに同居** | optionchan-gcp の `apps/viewer` にページと API を足す（このリポジトリは使わない or UI のライブラリだけ置く） | インフラ追加ゼロ。IAP・データの読み取りは既にある | optionchan-gcp が大きくなる。ビューアーのデプロイと一緒になる。別リポジトリにした意味が薄れる |
| **C. ローカルで動かす** | `npm run dev` などで手元で起動し、API は手元の gcloud の認証（ADC）で BigQuery を読む | インフラ・費用ゼロ。作りが一番単純 | 手元の PC でしか使えない（スマホ・外出先で見られない）。gcloud の認証が要る |
| **D. 静的ホスティング + データのエクスポート** | UI を静的サイト（GitHub Pages 等）に置き、板は optionchan 側で定期的に JSON に書き出して読ませる | 実行環境が要らない | JPX 由来のデータを公開の場所に置くことになる（利用規約の確認が要る。非公開にするなら結局認証が要る）。鮮度がエクスポートの間隔に縛られる |

**おすすめ: A**（開発中は C と同じコードで手元でも動かせるようにする）。理由:
- データの読み取りに認証が要る以上、IAP の後ろに置く A がビューアーで実績のある最短経路
- UI と API を同じサービス（同じオリジン）から出すので、IAP 越しの CORS・Cookie の問題が起きない（ビューアーの API を別オリジンから呼ぶ案は IAP の Cookie がオリジンごとで扱いにくい）
- 計算はブラウザなので、Cloud Run の負荷は板の JSON を返すだけ（最小インスタンス 0、費用はほぼ 0）
- C の動かし方（ローカル + ADC）は開発用として A のコードがそのまま兼ねる

A を選ぶ場合に決めること:
- GCP プロジェクト: optionchan と同じプロジェクトに置く（データセットの読み取りが同じプロジェクト内で済む）か、別プロジェクトから optionchan のデータセットを読むか
- IAP の OAuth クライアント: ビューアーと共用するか（同じプロジェクトなら共用できる）
- IaC: このリポジトリに Terraform を置くか、optionchan-gcp の `infra/` に足すか

## 7. 後段（MVP の後）

- 複数戦略の比較（同じグラフに重ねる・指標を横に並べる）
- 原資産 × 日数のヒートマップ（損益の色分け）
- 利益が出る確率・期待損益（IV に基づく対数正規。スマイルを反映したリスク中立分布は要検討）
- 証拠金の目安（JPX の VaR 方式の証拠金は再現が難しいので、目安の計算方法から検討）
- 過去時点の板で組む（optionchan の過去データ。移行完了後）
- 日経225ミニオプション（乗数 100、週次限月）

## 8. 技術の候補

- UI: TypeScript + Vite。グラフは軽量なもの（uPlot など。スライダー操作で毎フレーム描き直すので Canvas ベース）
- API: optionchan のビューアーと揃えるなら Python（Flask / gunicorn）。UI と同じ TypeScript（Node）にする案もある
- テスト: 価格モデル（Black-76・グリーク・IV の補間）を単体テストで固定する。既知の値（文献・JPX 公表のグリーク）と照合する
- リポジトリは optionchan-gcp と同じく汎用（プロジェクト ID 等を埋め込まない）
