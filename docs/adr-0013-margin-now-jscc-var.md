# ADR-0013: 今の必要証拠金を JSCC の VaR 証拠金の計算にする

- 状態: 採択（2026-11-23）
- 日付: 2026-11-23
- 関連: #382、#383（シナリオの点の再現。後続）、optionchan の #164（JSCC の 4 表）、[ADR-0002](adr-0002-margin-grid-approximation.md)（格子の概算）、[ADR-0011](adr-0011-margin-room-broker-formula.md)・[ADR-0012](adr-0012-futures-mark-to-market-room.md)（余力の式）、`docs/design.md` 5.10・7.1・7.3・13.1 K14

## 背景

- 必要証拠金は格子の最悪値 × 掛け目の概算（ADR-0002・#150）で、1 枚ずつの売りの 6 通りでは証券会社の額の 0.98〜1.07 倍に収まったが、組み合わせ（売りと買い・先物との組み合わせ）では大きくずれる。オーナーの口座の照合（2026-11-22。金額は書かない）では、売り put 2 枚・買い put 1 枚（同じ限月）の今の概算が証券会社の額の約 1.9 倍だった
- optionchan の #164 で、JSCC が毎営業日に公開する VaR 証拠金計算用パラメータファイル（1600 版 = 清算値段の確定後）の日経225 の分が 4 表（`jscc_var_scenario`・`jscc_var_scenario_set`・`jscc_var_parameter`・`jscc_ingest_runs`）に入った。1 枚の売り・買いの証拠金は JSCC の All-Instruments-VaR と全件一致する（optionchan の照合）
- 照合で分かったこと（手元の計算。値は書かない）:
  - 証券会社の「当社証拠金」= JSCC の VaR 証拠金額（ポートフォリオの符号つき ES。NOV 込み）× 1.0 で、±200 円で一致した（VI 先物は入っていないと読める）
  - 証券会社の「当社 NOV」は、算出日の **夜間の引けの約定値段**（取り込んだ板の最後のスナップショットの約定値段）で評価した NOV と 1 円単位で一致した（清算値段の NOV とは約 2.2 倍違う。照合は 1 件）
  - 必要委託証拠金 = 当社証拠金 − 当社 NOV（ADR-0011 の計算式）。当社証拠金の ES は NOV を含んだ値なので、NOV が 2 回効く（証券会社の保守寄りの形）
- JSCC の VaR 証拠金計算ソフトウェアの公開の仕様: VaR リスク額 = VaR 証拠金額（符号付）+ NOV で 0 以上、VaR 証拠金額は 0 以上。1 枚の OP の売りの「清算値段 × Contract Size が下限」はこの特別な場合

## 決定

1. **今（シナリオ 0）の必要証拠金だけ** を JSCC の計算にする: 必要証拠金 M = 掛け目 × V、V = max(0, ceil(ES 符号つき), ceil(−NOV_清算))。ES は H のシナリオの全部と S の小さい方から `stress_scenario_number` 本を集めた n 本の、小さい側 t = n × (100 − 信頼水準) / 100 本の平均（端数は按分）の符号を変えたもの。分子は BigInt の有理数で 1 円もずらさない（`model/jsccMargin.ts`）。pnl は 1 枚あたり（Contract Size を掛けない）
2. **NOV は今の板の評価価格**（格子と同じ `nov`）。所要額 = max(0, M − NOV)。NOV が V の中と所要額で 2 回効くのは証券会社の形をそのまま写したもの
3. 基準日 = 板の時刻の取引日（17:00 以降・休業日は次の営業日）の前営業日。その日の `succeeded` の取り込みだけを使う（古い日を使わない）。使えないとき（基準日のデータが無い = 平日 17:00〜18:30 ごろ・取り込みの失敗、銘柄が無い、集計グループが違う、枚数が整数でない、読めない、供給元に無い）は **格子の概算に戻し、理由を出す**
4. シナリオの点・テール・追証の線・追証マップ・過去の急落の再生・売りの効率・形のカード・AI の提案は格子の概算のまま（#383 で埋める）。シナリオの点が今と同じ点なら今の結果を使う
5. 出どころは文字で出す（タイルの副題に `JSCC 11/20`（基準日）/ `概算`、全文・内訳に理由）。色だけにしない
6. 設定「買いの OP で減らさない」の既定をオフ（相殺する = JSCC の形）にし、保存のキーを新しくする（`margin_exclude_long_options`。旧キーは読まない。#150 の前例）
7. サーバーは額を計算しない（計算はブラウザ）。`GET /api/jscc_scenarios?date=&i=…` は要求の銘柄の行だけを返す。`jscc_var_scenario` の 1 日のパーティション（約 131 MiB）はクラスタで絞っても同じ課金なので、**限月ごとに全行を 1 回読み**、(日, run_id, 限月) でキャッシュする。表の間の `jscc_run_id` が取り込みの記録と違えば使わない（取り直しの途中）

## 選ばなかった案

- **必要委託 = 当社証拠金（NOV を 1 回だけ）**: 口座の額と合わない（NOV の分だけ小さい）
- **NOV を清算値段で評価**: 口座の当社 NOV と約 2.2 倍違った（照合）。simulator の今の値段（アンカー IV の理論価格 / 今の値段）は約定値段に近い側
- **サーバーで額を計算して返す**: 「計算はすべてブラウザ」の作りに反し、足の編集・設定の切替のたびに往復する。行（1 銘柄 約 8〜10 KB）を返してブラウザで計算すれば、足の組み替えは往復なしで済む
- **銘柄ごとのクエリ**: 1 銘柄の等号でも 1 日のパーティション全部（131 MiB）の課金になる（実測）。限月ごとに 1 回読む方が安い
- **基準日のデータが無いとき前の日の値を使う**: 証券会社の 1 日固定と違う日の額になり、口座と合わない日の値を「JSCC」と表示することになる。概算に戻して理由を出す方を選んだ
- **シナリオの点も JSCC のシナリオで評価する**: 状態 S でのシナリオの値（OP はシナリオ後の評価額）を作り直す方法が要る（#383 の分析で、点ごとの再評価の仕方を決めてから）

## 結果

- 今の必要証拠金・所要額・余力は、データのある時間は証券会社の額に近い（照合の 1 件で ±200 円）。組み合わせのずれが無くなる
- 今のすぐ隣のシナリオの点は格子の概算なので、値が跳ぶことがある（組み合わせによっては 2 倍前後。「概算」の印と ⓘ・マニュアルで伝え、#383 で埋める）
- 平日 17:00〜18:30 ごろと取り込みの失敗の日は、夜間の板で概算に戻る
- 保存のキーの変更で、「減らさない」を自分で選んでいた利用者も「相殺する」に戻る
- 1 日のクエリ量 ≈ 触った限月の数 × 0.13 GiB × インスタンスの冷えたキャッシュ（BigQuery の結果キャッシュで 2 回目以降は 0 B）。D8（1 ジョブ 512 MiB 以下）の範囲
- 扱わないもの: 証拠金割増額・SAM・集計グループをまたぐ相殺（パラメータのレコード 1・2）・VI 先物・週次の OP（Weekly）。NOV の評価価格は今の板の値（気配の広い期近・深い OTM で証券会社の額と数百〜数千円ずれうる）
