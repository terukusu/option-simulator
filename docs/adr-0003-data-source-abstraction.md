# ADR-0003: 板の供給元を差し替えられるようにし、供給元に依らない部分を 1 か所に固める

- 状態: 採択
- 日付: 2026-10-19
- 関連: #154、`docs/data-sources.md`、`docs/design.md` 4 章・7.1・7.4・13.1 K5・K8

## 背景

板は optionchan（JPX のページを毎分取り込んで BigQuery に蓄積するツール）からしか作れなかった。オーナーの狙いは、JPX のページの取り込みに依らず、**利用者が自分で契約した正規の API（証券会社の API・有料のデータ API）** を供給元にして、誰でも clone して自分の環境で使えるようにすること（2026-10-19）。

調べると（`docs/data-sources.md` 1 章）:

- 行使価格ごとの気配を毎分以上で取れるのは証券会社の API（kabu ステーション API・Interactive Brokers。立花 e 支店 API は先物・オプションの時価が未確認）。J-Quants は日次で気配が無い
- kabu ステーション API は手元の PC のアプリ（localhost）が要り、登録銘柄は 50 まで。利用条件に「第三者が作成されたプログラム等を利用することを禁止」「加工…禁止」がある
- 画面は板の JSON 版 1 の形だけに依存し、価格モデルは気配からブラウザで計算している。JPX 固有の項目（気配の IV・JPX グリーク・建玉・ATM の表示・清算値）は無くても計算は回るが、気配の IV が全行に無いと「JPX の IV 欠損」の印が全セルに付き、板の IV 列が空になっていた

## 決定

- **板の JSON は版 1 のまま** にし、項目を「必須（気配・行使価格・限月の日付・先物と時刻）」と「供給元によって欠けうる（null 可）」に分けて契約として文書化する（`docs/data-sources.md` 2 章・`data/chainTypes.ts`）
- 画面は欠けに耐える: 板全体で気配の IV が無ければ「JPX の IV 欠損」の印を出さず、板の IV 列は気配の価格から Black-76 で求める。遅れ 0 分は「遅れなし」、optionchan 以外の API のカレンダーは「API の版」と出す
- API に **供給元の口**（`sources.DataSource`）と `DATA_SOURCE` の値 → 実装の表（`sources.BUILDERS`）を置く。optionchan の読み方（`ChainService`）は中身を変えずにその実装の 1 つにする
- 2 つ目の実装は **中立の「気配の一覧」JSON → 板の JSON 版 1 の純関数**（`quotes.py`）と、それをファイルから読む供給元 `DATA_SOURCE=quotes`。限月の日付・行の組み立て・reason・使える板の判定・板の形は optionchan の板と同じコードを通す。供給元ごとの違いは「自分の API から気配を取り出してこの形に書く」部分だけになる
- 特定の証券会社の API を呼ぶアダプタはリポジトリに置かない（今は）。既定の供給元は optionchan のまま（13.1 K5・K8 は変えない）

## 検討した選択肢

| 案 | 良い点 | 悪い点 |
|---|---|---|
| A. 中立の気配の一覧 + ファイルの供給元（採択） | 共通部分が 1 か所でテストできる。利用者は自分のスクリプトで気配を書くだけ（手元の PC のアプリが要る API でも、Cloud Run と分けて動かせる）。口座の無い CI で確かめられる | ファイルを書く側（利用者のスクリプト）は利用者が用意する。書き出しの間隔・鮮度は利用者次第 |
| B. kabu ステーション API のアダプタ（生の応答 → 板）を API に入れる | 設定だけで kabu の板が出る | 口座が無く合成の応答でしか確かめられない。localhost の API なので Cloud Run からは呼べない。50 銘柄の上限。利用条件（第三者のプログラム・加工の禁止）に合うか不明 |
| C. J-Quants の日次の値で板を作る | クラウドから呼べる・JPX 公式 | 気配が無く、今の画面（気配の mid から F・スマイル）が成り立たない。清算値モード（後段）の設計が先に要る |
| D. 板の JSON を供給元ごとのデータ形式に広げる（形式のバージョン 2） | 供給元の項目をそのまま運べる | 画面・保存・file アダプタの後方互換を壊す。計算に要るのは気配だけで、広げる利点が小さい |

## 結果

- 良い点: optionchan が使えなくなっても、気配を書き出せる API があれば同じ画面が動く。供給元を足すときの作業が「気配を中立のデータ形式にする写像」とアダプタの実装だけになる。optionchan の挙動・費用は変わらない
- 悪い点: IV 推移（`/api/atm_iv`）・日次の値（`/api/atm_daily`）は optionchan の表に依存したままで、他の供給元では 503（IV 推移・追証マップの過去の点が出ない）
- 残り: kabu ステーション API の条件の解釈（オーナー判断・証券会社への確認）。条件に合う証券会社のアダプタ、清算値モード（J-Quants）は別 Issue で
